# RCA — Future Stars League (torneo-platform): public `/api/*` returns Cloudflare 520

## Symptom
Public homepage renders its shell/header/footer, but the in-body public data call (`GET /api/public/...`, e.g. `/api/public/home`, `/api/public/tournaments`) shows the Cloudflare origin-error text ("origin returned an empty/unparsable response"). Screenshot taken ~09:25 local (CEST = 07:25 UTC), right after a redeploy.

## Verified findings (production, active run `45e55342-ceaa-4d65-b85a-2dd171157754`)
- **Live probes:** `GET /api/public/tournaments` and `/api/public/home` return **HTTP 520** consistently (5+ consecutive probes), body `error code: 520`. `GET /` and `/health` return **200 with the SPA `index.html`** — i.e. served by the Cloudflare edge/R2 static layer, which is healthy. So the failure is isolated to the `/api/*` → Kubernetes backend origin route; the frontend edge is fine (matches "shell renders, body API call fails").
- **This is NOT the app code.** Production logs show the exact public endpoints returning **200 OK** in volume (`/api/public/tournaments`, `/api/public/tournaments/la-serie-a-dei-bambini`, media, bracket, schedule, etc.). Startup completes cleanly: `Application startup complete` + `fsl.showcase ... Showcase demo content ready`. `org_clubs_backfill()` / migrations do NOT crash or hang the app.
- **Root cause = GKE node failure + pod reschedule gap (infrastructure):**
  - Node `gk3-emergent-default-clu-nap-jw8zzlht-6a2bdb75-ctnm` (hosting the serving pod `...-wwp8f`) went **NodeNotReady at 07:21:47 UTC** (= ~09:21 local, matching the screenshot).
  - Taint manager **marked `wwp8f` for deletion at 07:28:13 UTC**; pod is now `deleting:true`.
  - Replacement pod `...-4dp5z` created 07:28:17 UTC on a healthy node (`...-f86a6347-h7j9`), currently **Pending / ContainerCreating** (pulling the 576 MB image).
  - During this window the backend Service has **no Ready endpoint**, so the Cloudflare worker's `/api/*` origin calls get an empty/reset response → **520**. `fetch_app_logs` for the last 15 min returned **0 application lines** — confirming requests aren't landing on any backend pod during the gap.
- **Not OOM / not a crash loop:** `wwp8f` restart_count = 0, no OOMKilled, no exit 137. The earlier `z97lg` "Startup probe failed: 503" events (07:09:03–07:09:29) were the normal ~20s cold-start window (migrations + backfill run before uvicorn binds :8001); that pod completed startup and was later removed by a routine scale-down (2→1), not a crash.
- Tier: `tier_0` (Starter), 2 fixed replicas, no HPA, 512Mi mem limit / 250m CPU limit. Resource limits are NOT implicated.

## Is it transient or persistent?
**Transient / self-healing.** Kubernetes is already rescheduling the backend onto a healthy node. The 520 persists only until pod `4dp5z` passes its startup probe (~20–30s after image pull completes), at which point the Service regains a Ready endpoint and `/api/*` returns to 200 automatically. No redeploy is required.

## Contributing factor (resilience, not root cause)
The backend's startup runs migrations + `org_clubs_backfill()` **before** uvicorn binds :8001, so a freshly-rescheduled pod takes ~20–30s before it can serve. Combined with effectively one serving replica during a node loss, this **widens the no-endpoint window** whenever a node is evicted/rescheduled, turning a brief infra blip into a visible ~1–2 min `/api/*` outage.

## Recommended actions
1. **Platform / infra (primary):** The trigger is a GKE node NotReady + taint eviction — Emergent-managed infrastructure, self-healing. If 520s on `/api/*` persist more than a few minutes after pod `4dp5z` reaches Ready, escalate to Emergent platform support (quote deployment `torneo-platform`, run `45e55342-ceaa-4d65-b85a-2dd171157754`, node `...-6a2bdb75-ctnm`).
2. **Code (optional hardening, reduces blast radius of any future reschedule):** Move `org_clubs_backfill()` (and any other heavy startup work) to run in a background task **after** uvicorn binds the port, so a rescheduled pod can serve `/api/*` immediately and only backfills asynchronously. This shortens the no-endpoint window during node churn. This is a resilience improvement, not the cause of today's incident.
3. **User / verify:** Reload the public site (hard refresh) once the new pod is Ready — the body `/api/public/...` call should return to normal without any redeploy.
